## 1. Read-only posture (SIFTMesh does not modify originals)

- The original evidence at `/home/sansforensics/projects/ev_disk` (1 file(s)) is treated as **read-only**.
- SIFTMesh opens every original in binary read mode only and **never** writes to a source path.
- All SIFTMesh-controlled writes are forced through a central path-policy write-gate that rejects
  any target outside the run directory or inside the original evidence tree.
- **Scope of the software guard:** this is enforced for SIFTMesh's own code paths (no raw shell, no
  destructive tools - see the safety policy). It is recorded as `enforcement: posture_only` in
  `evidence/readonly_mounts.json`; it is **not** OS-level read-only mount enforcement
  (`mount -o ro` / `blockdev --setro`), which is a documented Linux enhancement deferred to a
  later stage.

## 2. Working copies vs. read-only-in-place (large-evidence strategy)

For large datasets (tens to 100+ GB: archives, disk/memory images, photos), SIFTMesh uses
**read-only access in place plus a cryptographic seal** instead of the classic
"duplicate → operate → delete" working-copy doctrine:

- Each artifact is hashed once (SHA-256, streamed in constant memory) at ingest; that hash is the
  custody baseline for source-integrity checks.
- This avoids the prohibitive storage/time cost of duplicating 100+ GB while preserving a
  re-verifiable software integrity record.
- A working copy is made only for the rare operation that must *mutate* an artifact (which SIFTMesh
  forbids by default); if ever needed, only that single artifact is copied into the run directory
  as a hash-verified **derived** artifact - the original is never touched.
- **Seal-what-you're-pointed-at:** SIFTMesh seals whatever path it is given as "the original."
  Whether that path is already an examiner's forensic working-copy is an upstream decision.

## 3. Archives and disk/memory images

- Archives (ZIP/TAR/…) and disk/memory images are hashed **as given** - one manifest entry per
  artifact. `init-case` does **not** recurse into or extract them.
- Extraction/parsing is a later *derived* operation, recorded in `evidence/derived_artifacts.json`
  with a provenance link back to the source artifact and its SHA-256.

## 4. Hashing standard

- Algorithm: **SHA-256** over the full byte stream of each file.
- `evidence/evidence_manifest.json` holds the typed manifest (path, sha256, size, mtime, type).
- `evidence/hashes.sha256` is GNU coreutils compatible; verify on Linux with:
  `cd "/home/sansforensics/projects/ev_disk" && sha256sum -c <run>/evidence/hashes.sha256`.

## 5. Chain of custody

- `evidence/custody_log.jsonl` records validated `CustodyEvent` entries for SIFTMesh ingest and
  verification actions, with the source SHA-256, actor, tool name/version, and UTC times.
- This aligns with documentation and integrity principles from **ISO 27037**, **SWGDE**, and
  **NIST SP 800-86** (auditability, repeatability, reproducibility, justifiability). It does not
  claim write-blocker, bit-stream acquisition, or human signatory custody compliance.

## 6. Treat case data as hostile (prompt-injection stance)

- Every string drawn from evidence is treated as **data, not instruction**. Content inside
  artifacts can never alter SIFTMesh's control flow, tool permissions, or safety policy.

## 7. Non-goal

- This process is designed for analyst-grade reproducibility and audit. It is **not** a claim of
  court admissibility.
